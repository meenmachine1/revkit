# revkit binary diffing / version tracking: design recommendation

Scope: match the functions of two programs in one project, show what changed, port names/types/prototypes/comments from the analysed program to the new one. Advisory only; measurements below are from scratch runs (`bsim_stability.py`, `bsim_stability_*.json` beside this file) on the **tuning** corpus (held-out untouched).

## 0. What BSim actually does (vendored sources, `third_party/ghidra/decompiler`)

- Entry point: `SignaturesAt::rawAction` (`signature_ghidra.cc:38`): runs the function through the **`normalize`** action group, not `decompile` (`coreaction.cc:5489`), then `simpleSignature(fd, encoder)`. `normalize` keeps base, protorecovery(_b), deindirect, localrecovery, deadcode, stackptrflow, stackvars, deadcontrolflow, fixateproto, nodejoin, unreachable, subvar, normalizebranches; it drops typerecovery, blockrecovery (structuring), switchnorm, cleanup, split*, merge, casts, fixateglobals, bitfields, returnsplit, doubleload. So features are computed on SSA p-code after dead-code elimination, stack-variable recovery and branch normalization, before any type or variable-merge decision, and are therefore independent of user names and types.
- Features (`signature.cc`): one 32-bit hash per feature, three kinds.
  1. `VarnodeSignature`: a Weisfeiler-Lehman style hash of the data-flow neighbourhood of each written Varnode. `SignatureEntry::localHash` (l.268) hashes size (collapsed to ≤4 under `SIG_COLLAPSE_SIZE`), constant-ness (the value only without `SIG_DONOTUSE_CONST`), input-ness, persistence, and the defining opcode; `hashIn` (l.321) folds in the inputs' previous-round hashes, order-insensitive for commutative ops and MULTIEQUAL; `maxiter = 3` rounds (`GraphSigManager` ctor, l.926), so each feature covers a depth-3 cone. Shift/truncation amounts and CALL/LOAD/STORE address operands are excluded (`SignatureEntry` ctor, l.144). COPY/INDIRECT/CAST chains are collapsed into the source ("shadow"); with `SIG_COLLAPSE_INDNOISE` the collapse is the dominator-based `removeNoise` (l.456) over COPY/INDIRECT/MULTIEQUAL edges, which is what removes register-allocation and spill noise.
  2. `BlockSignature`: per basic block, hash of (in-degree, out-degree) mixed one round with predecessors and true/false edge sense (`BlockSignatureEntry::hashIn`, l.586) plus a call count; and "form 2" pairs of consecutive expression roots (CALL, STORE, CBRANCH, RETURN, BRANCHIND) with their data-flow hashes (`collectBlockSigs`, l.767).
  3. `CopySignature`: one per block, an order-free bag of stand-alone constant/input copies (argument setup).
- Settings actually used (`lshweights_64.xml`, attribute `settings="0x4d"`): `SIG_COLLAPSE_SIZE | SIG_COLLAPSE_INDNOISE | SIG_DONOTUSE_CONST`, i.e. **constants are not hashed**; `GenSignatures.getWeightsFile` picks `_32`/`_64`/`_nosize` by pointer size.
- Java side (`generic/lsh/vector`): `LSHCosineVector.installFeatures` turns the sorted hash list into (hash, tf, idf) entries; `coeff = idfweight[idf] * tfweight[tf]` (`WeightFactory.getCoeff`), idf being the hash's document count from the 1000-entry `idflookup` (anything unseen gets the maximal weight). `compare` is cosine on these coefficients (`LSHCosineVector.compare`), and **confidence/significance** is `dot - numflip*(flip0+flip1/max) - diff*(diff0+diff1/max) + addend` (`LSHVectorFactory.calculateSignificance`), a log-likelihood-ratio under a hash flip/add/remove noise model. LSH (`KandL`, `Partition`) is only for database search; the VT BSim correlator does a `BinningSystem` over the two programs instead. Default search threshold 0.7 (`QueryNearest`).
- Ghidra's own VT+BSim correlator (`VersionTrackingBSim`, `BSimProgramCorrelatorMatching`) is the closest prior art to what I propose: seeds = unconflicted pairs with confidence ≥ 10 and call-graph fan-out ratios ≥ 0.5, then two rounds of implication through parent/child (and namespace) neighbourhoods, best unconflicted pair first, confidence adjusted by child/parent/length ratios.

### Measured (Ghidra 12.1.4 headless, i9-14900F, 8 workers)

| program pair (debug builds, names = truth) | common fns | median cos | ≥0.7 | top-1 (strict) | top-1 by feature count <10 / 10-29 / 30-99 / ≥100 |
|---|---:|---:|---:|---:|---|
| cjson x86-64 gcc-O0 vs clang-O0 | 122 | 1.00 | 90% | 59% | 41 / 47 / 94 / 100% |
| cjson x86-64 gcc-O2 vs aarch64 gcc-O2 | 94 | 0.73 | 52% | 46% | 24 / 23 / 72 / 83% |
| cjson x86-64 gcc-O2 vs clang-O2 | 94 | 0.50 | 18% | 44% | 33 / 26 / 57 / 100% |
| cjson x86-64 gcc-O0 vs gcc-O2 | 95 | 0.20 | 16% | 32% | 23 / 14 / 70 / 100% |
| zlib x86-64 gcc-O2 vs riscv64 gcc-O2 | 138 | 0.62 | 42% | 73% | 16 / 82 / 79 / 89% |
| zlib x86-64 gcc-O2 vs clang-O0 | 141 | 0.52 | 25% | 73% | 45 / 61 / 81 / 89% |
| lua x86-64 gcc-O2 vs aarch64 clang-O2 | 629 | 0.59 | 39% | **78.5%** | 51 / 83 / 82 / 94% |

Top-1 is strict (ties lose), from the body alone, no propagation. Findings:
1. BSim's invariance is to the **ISA**, not the compiler: same-compiler cross-ISA pairs score higher than same-ISA cross-compiler pairs, and -O0 vs -O2 is nearly hopeless by body alone (inlining changes the graph). Same compiler, same -O, cross-ISA is the firmware case and works well: 72-94% top-1 on anything with ≥30 features.
2. BSim's default 0.7 threshold is far too strict for diffing (only 39% of true lua pairs reach it); ranking plus mutual-best plus propagation must replace absolute thresholds.
3. Functions with <10 features (getters, wrappers, thunks) are undecidable by body; they are the job of call-graph propagation and reference tiers.
4. Cost: the normalize+signature pass is **not** cheap: 4.3 ms/function on lua, 6.3 on zlib single-threaded, versus 5.0/8.4 for a full decompile through `DecompInterface` (incl. its IPC and printing). So ~80% of a decompile. At libLLVM scale (127k functions, 33 min for a full decompile at 8 workers) that is ~20-25 minutes of signatures. It cannot be the first tier.

## 1. Matching architecture

**Per-function fingerprints, as fact-engine queries** (`diff.features(program, entry)`, memoized, dependent on `analysis.flow`/`analysis.function` and the bytes; see §4 for the dependency discipline):

| tier | feature | from | cost | invariance |
|---|---|---|---|---|
| F0 | name (DWARF/PDB/export/user) | facts | free | exact only |
| F1 | relocated byte hash: bytes with relocation/immediate-address fields masked using the lifter's operand info | bytes + p-code | µs | same build, moved code |
| F2 | mnemonic + raw-p-code-opcode sequence hash | `analysis.flow` + SLEIGH (already decoded) | µs | register renames, address moves |
| F3 | CFG shape: BinDiff MD-index (sorted (in,out,topological order) edge tuples with sqrt-prime weights) of blocks+edges, loop count, block count, instruction count, prime signature of p-code opcodes | FlowGraph | µs | compiler-stable, ISA-sensitive only via instruction counts |
| F4 | reference bags: called imports / named callees, string constants, large immediates, MMIO/global addresses (as targets, not values), callee count, caller count | FlowGraph.refs/data_refs, strings | µs | very stable across everything |
| F5 | BSim vector (above) | decompd worker, new mode `signature` | ~5 ms | ISA, register allocation, scheduling |
| F6 | decompiled C AST hash (Diaphora-style: AST with identifiers and constants abstracted) | existing `tokens` decompile | ~6 ms | less than F5 (types, merges); keep for UI "unchanged" marking, not matching |

**Match driver: BinDiff-style ordered unique matching + propagation, not a global assignment.** Hungarian/global assignment on an n×m similarity matrix is O(n²) memory (10⁵×10⁵ is impossible), is not explainable ("why this pair?" has no answer), and inverts the real signal: in version diffing most functions have *one* exact match and the hard cases are local. The procedure:

1. **Exact tiers, globally unique**: for each of F0, F1, F2, (F3+F4 combined) build hash → functions on each side; a hash with exactly one function on each side is a match with that tier's confidence (name 1.0 when both sides carry debug/export names; bytes 0.99; p-code sequence 0.97; shape+refs 0.9). Ambiguous buckets (k-to-k) are deferred, not matched.
2. **Propagation** (the step BinDiff and the VT BSim correlator both found decisive): from every matched pair, consider the callees of both in call order, the callers, and the functions sharing a data reference (same string, same global); re-run the exact tiers *within those neighbourhoods*. A hash unique within the neighbourhood of a confirmed pair is a match ("call-site-order", "common caller", "same string" evidence; confidence 0.8-0.9 scaled by the parent's). Iterate to fixpoint. This is what resolves the tiny functions and the k-to-k buckets.
3. **Similarity tier** for what remains: compute F5 only now, for the unmatched functions on both sides (typically <10-20% after version bumps; everything for cross-compiler). Candidates for a function = top-K (K=16) by a cheap prefilter (F3 block-count/loop-count/callee-count within a factor 2, shared F4 references) then BSim cosine; accept a pair when it is mutual best, cosine ≥ 0.35 and BSim significance ≥ 10 (its seed threshold), *or* lower when a propagation edge corroborates it. Confidence = calibrated from the benchmark (§5), reported as the tier plus the evidence list.
4. **Ties and conflicts**: never auto-match a tie; emit a `candidates` list for the UI. A later higher-confidence match that contradicts an earlier auto-match replaces it (an accepted user match is never replaced; it blocks conflicting candidates like VT's `BLOCKED`).
5. Report per pair: tier, confidence, similarity (BSim cosine where computed, else 1.0 for exact), and the evidence (which hashes, which neighbour pair implied it), and per unmatched function: the reason (no candidate / tie among {…}).

Everything is deterministic: tiers run in fixed order, buckets and neighbourhoods are processed in address order, ties break on nothing (they stay ties).

## 2. P-code specifically

- **Level.** Use both ends and skip the middle: raw lifted p-code opcode sequences (F2) for the exact tier, and the decompiler's post-`normalize` SSA (F5) for similarity. A home-grown "normalized raw p-code" (renaming registers/temps, abstracting addresses) is the layer I reject: it would reinvent `removeNoise`, dead-code elimination and stack-variable recovery that `normalize` already does, deterministically and identically to Ghidra's, and would still not survive scheduling or instruction selection. The one normalization worth doing on raw p-code is cheap and lossless: F2 hashes opcode + operand *kinds* (const / register / unique / ram / stack-relative) and sizes, never register numbers, never addresses, with constants that are mapped addresses replaced by their reference kind. That already removes register allocation and relocation.
- **What survives cross-architecture:** per the measurements, BSim's data-flow hashes do (same compiler/-O), reference bags (F4) and CFG shape (F3) do; byte and instruction tiers don't; raw p-code opcode sequences only partially (x86 flag computations, ARM conditional execution, RISC-V's split immediates all add ops). For the firmware gates (same sources, several processors) expect F4+F3 seeds plus propagation to carry most of it and F5 to decide the rest; -O-level differences are where everything degrades, and no fingerprint fixes inlining; propagation through the call graph of what *didn't* inline is the only honest answer.
- **How to compute F5 in revkit:** add `Mode::signature` to `decompd` (`bundle.h` Mode enum, a `Session` registered through `register_mode`). The session is `InputDecompiler` with `allacts.setCurrent("normalize")`, no printer, and `simpleSignature`/`getSignatureVector` on the `Funcdata` (hashes only; drop the `<call>` records, we have the call graph). Payload = sorted u32 vector. Two decisions: (a) the bundle for this mode must be **stripped**: function starts/bodies, import and external names, no-return, flow overrides, read-only ranges, and *no* user names, types, comments or prototypes; otherwise retyping a callee invalidates callers' signatures and the memo churns for nothing; (b) `SigManager::settings` is a process-wide static — set it once per worker (0x4d, to share Ghidra's weights). A worker process keeps two architectures by arch key; mode is part of the key, so signature sessions and decompile sessions co-exist.
- **Weights:** vendor `lshweights_64/32/nosize.xml` (Apache 2.0) and implement the 150 lines of `LSHCosineVector`/`WeightFactory`/`calculateSignificance` in C++ (`src/diff/lsh.cc`); no LSH buckets needed for pairwise diffing (candidate prefilter does that job). Later, revkit-specific idf tables can be re-derived from the corpus.
- **Cost at scale:** libLLVM-sized: F0-F4 for 127k functions is seconds (they read what `analysis.flow` already holds). F5 for the residue only; a version bump leaves a few thousand unmatched → tens of seconds at 8 workers. Full cross-compiler diff of 100k functions is the 20-minute case and runs as a background analysis with progress, memoized per function so a second diff against a third version pays nothing.

## 3. Basic-block and instruction diff inside a matched pair

Ghidra's `HashedFunctionAddressCorrelation` (SoftwareModeling `program/model/correlate`) is the right algorithm and worth porting rather than BinDiff's: n-gram hashes of instruction mnemonics within basic blocks, largest-n unique n-grams matched first, then extended along the block, then disambiguated by matched parents/children/bytes (`DisambiguateByParent/Child/Bytes`), producing a source→destination instruction map. revkit version: n-grams over the **F2 p-code-kind tokens** rather than mnemonics (so it works cross-ISA within reason), seeded by block pairs whose BSim `BlockSignature` hashes (we get them for free from F5 in debug mode, `debugSignature`) or F3 position agree, then LCS inside matched blocks for instruction-level alignment. Output per pair: block map (matched / added / removed / modified), instruction map, and a diff of F4 (references that changed). Decompiled-C side-by-side: run the existing `tokens` decompile on both, map tokens through the instruction map (tokens already carry instruction addresses), and LCS on the token lines for the residue; mark lines unchanged / changed / only-here. Same machinery drives the listing and graph views: the graph view colours blocks by block status and lays both graphs out with the matched blocks pinned to the same row.

## 4. Carrying analysis across (facts)

- **Match set = a diff session object**, stored as a `NOTE` in the project space (like a program record) plus one assertion per *accepted* match: `FactKind::Match` (new kind; key `{program_b, entry_b}`, sub = `program_a`, value = `entry_a` + tier + confidence), `depends_on` the `FunctionBounds` assertions on both sides when they exist. Auto-proposed matches are a **derived query** (`diff.matches(session)`), never assertions: they recompute when either side's functions change, which is exactly the incremental re-diff (fingerprint revalidation makes an unchanged function's features a cache hit; only the propagation step re-runs, and it is seconds). A user accepting a match turns a derived row into an assertion; rejecting one asserts a `Match` with value "none"/blocked so the query won't propose it again (the query reads the accepted/blocked set as an input: accepted pairs are seeds, like VT's `useAcceptedMatchesAsSeeds`).
- **Ported markup** = ordinary assertions on program B with provenance `Provenance{kind: Migration (rank = import, below user), id: "diff", version: <session id>, session: <apply run id>, reason: "from <prog_a>@<entry_a> (<tier>, conf)"}`. Add a `diff` id convention rather than a new kind: Migration already ranks below user and above agent/analysis, so a user's later edit in B wins and B's DWARF import (if any) ties by recency. Each ported assertion `depends_on` the `Match` assertion it came from: retracting the match (or the user's undo) kills every fact ported through it in one op, and undo of that revives them — the existing liveness machinery, no new code. `RevertByProvenance{Migration, session}` reverts an apply run.
- **Which items:** names (apply only where B's name is default or came from the same diff earlier: VT's `REPLACE_DEFAULT_ONLY`), prototype and parameter names/types (with the type closure `DefineType`d into B by hash; `BindTypeName` not re-applied automatically), comments by instruction map (plate/pre at the function or matched block; eol/post only where the instruction matched), locals by storage key only when the storage matched in the instruction map, notes/bookmarks at the function. Offer VT's `ADD` for comments (append, never overwrite).
- **Source edited later:** nothing moves automatically. The ported fact records the source op id (`meta`); a derived query `diff.stale(session)` lists ported facts whose source key's effective value differs from what was ported (reads A's keys through the engine, so it is incremental). The UI shows a "stale" badge with "re-port"; re-port = retract + assert in one transaction. Auto re-port is a per-session option off by default: silent changes to B are what users hate about VT's "apply".
- **User-accepted vs auto:** both are `Match` assertions once applied; the difference is `prov.kind` (`User` vs `Migration`) so `blame` says "accepted by alice" vs "auto (tier bytes, 0.99)". Apply policy: auto-matches ≥ 0.95 may be applied in bulk; lower ones need acceptance or an explicit "apply ≥ threshold" with the threshold recorded in `reason`.
- **Collab:** sessions and matches replicate like any ops; features and proposals are derived and recomputed per daemon.

## 5. Evaluation

Ground truth from the corpus's debug builds (`out/corpus`, `rk-debuginfo` names; a function's truth identity = its DWARF name + compilation unit, deduplicated: names occurring more than once on a side are excluded from scoring, as in my script). Pair families: same program, (a) adjacent versions (needs 2-3 source versions of zlib/lua/cjson built by `build.py`; the cheap and most important family), (b) -O0/-O2, (c) gcc/clang, (d) x86-64/aarch64/riscv64, (e) the firmware gates' multi-processor builds, plus the stripped twin of each binary as the *input* so names never leak into matching. Metrics per pair and aggregate: precision/recall/F1 of the proposed match set against the truth, broken down by tier, by feature-count bucket, and by change kind (unchanged / modified body / renamed-only / added / removed, derived from truth plus byte identity); top-1 accuracy of the F5 tier alone (what I measured); markup port accuracy (a ported name is right iff the truth names agree). CI gates on the tuning corpus (`scripts/ci.sh --diff`): precision ≥ 0.99 on auto-applied matches for family (a) and recall ≥ 0.9; baselines guarded for the other families; held-out measured once as `heldout.md` prescribes. **BinDiff comparison:** feasible — GitHub reachable; BinDiff 8 ships a `.deb` and a Ghidra BinExport extension (the user runs the sudo install); score BinDiff's `.BinDiff` SQLite output with the same truth, and VT via a headless `AutoVersionTrackingScript`-style PyGhidra run (its correlators are scriptable: `VTSession`, `VTMatchSet`). Report both as columns beside revkit per family; the honest expectation is parity on (a) and better on (d)/(e) because of F5 and F4.

## 6. API, UI, scale, determinism

- **`DiffService`** (new proto): `CreateDiffSession{project, program_a, program_b, options}` → session id; `RunDiff{session}` (long-running: `GetDiffStatus`, cancel) reusing `AnalysisService`'s job shape; `ListMatches{session, filter: tier/confidence range/status/change kind/name contains, page}` → rows {entry_a, entry_b, names, tier, similarity, confidence, status, change_kind, evidence}; `ListUnmatched{session, side}` with candidates; `GetFunctionDiff{session, entry_a}` → block map, instruction map, reference diff, both token streams with line status; `AcceptMatches`/`RejectMatches`/`SetMatch{entry_a, entry_b}` (manual) → assertions; `ApplyMarkup{session, pairs|min_confidence, items, policy}` → one revision, counts; `ListStale{session}`; `RevertApply{session, run}`. Subscriptions: a `DIFF_SESSION` invalidation kind when either program's function list changes.
- **UI flow:** Tools → Compare: pick A (analysed) and B (new) from the project (or import B into the project in the same dialog); a run with progress; the match table (sortable, filters as above, colour by confidence, status column) over a side-by-side view (listing / graph / decompiler, synchronized scrolling through the instruction map; unchanged lines dimmed); keyboard accept/reject; "Apply markup" with the item checklist, threshold and policy; a stale-badge pass afterwards. The function panel in B gets a "matched" column.
- **Performance targets:** 10k functions: features + exact tiers + propagation < 2 s, F5 residue < 10 s, interactive accept/reject < 50 ms (assertion commit + incremental query). 100k: exact tiers + propagation < 30 s; F5 on a 10% residue < 2 min at 8 workers; full F5 everywhere (cross-compiler) ≤ 25 min, resumable, memoized. Memory: features ≤ 200 bytes/function except F5 (≈ 4 bytes × ~45 features median; keep under 1 KB/function; libLLVM ≈ 100 MB).
- **Determinism:** all queries are pure functions of snapshots of A and B; tie-breaking never depends on iteration order (buckets by address, neighbourhoods in call order); the decompiler worker output is already byte-identical across `-j` (join records don't affect normalize-level SSA hashes, but verify in a test: same vector at `-j 1` and `-j 8`). `simpleSignature` sorts the hashes.

## 7. Risks and milestones

Risks, most likely failures first: (1) `normalize`'s dependence on callee prototypes (`protorecovery_b`): a stripped bundle gives different vectors from Ghidra's, which breaks nothing but means Ghidra's idf tables are slightly off; measure and re-derive. (2) Inlining and -O-level changes: no tier fixes it; make the UI honest (unmatched with candidates) rather than forcing matches. (3) Tiny functions tie: rely on propagation; precision on those must be gated separately. (4) F5 cost surprises on huge functions (BSim has `maxvarnode` for a reason): cap by varnode budget using the existing `DecompileBudget`, mark as "no signature". (5) Function discovery differences between the two sides (bodies split or merged) corrupt every tier; report body-mismatch as its own change kind. (6) Ported types with conflicting names in B (`BindTypeName` semantics): never auto-bind, only define.

Milestones:
- **M1 (user value first): same-ISA firmware version diff with name/comment porting.** F0-F4, unique matching, call-graph and data-reference propagation, the `Match` fact kind, session object, match table, apply names/comments/prototypes with `depends_on`, undo. Benchmark family (a) and gate (e) on the firmware corpus. No decompiler involvement, so it is fast and ships in weeks.
- **M2: similarity.** `Mode::signature` in decompd, C++ LSH cosine/significance, F5 residue matching, candidate lists, confidence calibration, families (b)-(d), BinDiff/VT comparison columns.
- **M3: inside-function diff.** Block/instruction correlation, side-by-side listing/graph/C, comment porting by instruction, stale detection and re-port.
- **M4: scale and polish.** 100k-function targets, background runs, incremental re-diff on edits, cross-arch firmware gate across all processors, idf re-derivation.

Rejected: learned embeddings (Gemini/SAFE/jTrans/asm2vec). No GPU, non-deterministic training, unexplainable scores, and the literature's cross-compiler gains over BSim-class features are modest on exactly the hard cases (inlining) where nothing works; the engineering budget is better spent on propagation and the benchmark. Diaphora's pseudocode/AST hashes: kept only as F6 for "unchanged" display, since they depend on type recovery and merging that users change. Global assignment: rejected above (§1).
